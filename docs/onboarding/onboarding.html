2. Background ideas you need

Skim the ones you already know. Everything later builds on these.

Large language model (LLM) and Claude

An LLM is a program that takes text in and produces text out. Claude is the LLM this repo uses. LLM output is probabilistic: ask twice and you may get two different answers, and some of them will be wrong. That one fact drives the whole design of agentflow. Never trust an answer you haven't checked.

Claude Code and claude -p

Claude Code is Anthropic's command-line program for working with Claude. Normally it's interactive. claude -p ("print mode") runs it once without a human: you send a prompt on standard input, and it prints the answer and exits. With --output-format json the answer comes wrapped in a JSON "envelope" that also reports cost (total_cost_usd) and errors (is_error). agentflow calls Claude this way, as a subprocess.

Agents, tools, hooks, skills

  • Agent: an LLM running in a loop that can take actions. In Claude Code, an agent can use tools (read files, run shell commands).
  • Hook: a script Claude Code runs automatically at certain moments. A PreToolUse hook runs before a tool is used and can allow it, ask the human, or deny it.
  • Skill: a Markdown file (SKILL.md) of instructions that Claude Code loads when relevant. It starts with "frontmatter", a block between two --- lines holding a name and description.
  • Subagent definition: a Markdown file in .claude/agents/ describing a specialised role.

Graphs, DAGs and topological order

A graph is a set of nodes connected by arrows (edges). Here a node is a task, and an arrow A → B means "B needs A's output". A DAG (directed acyclic graph) is a graph with no loops: you can never follow arrows back to where you started. A topological order lists the nodes so every task comes after everything it depends on. Python's standard library has graphlib.TopologicalSorter, which computes this and detects cycles.

flowchart LR A[fetch sales] --> C[summarize] B[fetch costs] --> C C --> D[publish]

A DAG. The two fetches don't depend on each other, so they can run at the same time.

asyncio

Python's built-in way to run many things at once in one thread. A function marked async can pause at await while waiting (for a network call, a subprocess, a timer) so others can run. asyncio.Semaphore(n) lets at most n things into a section at once. asyncio.to_thread runs an ordinary (blocking) function in a background thread so it doesn't freeze the others.

SQLite

A database stored in a single file, built into Python as sqlite3. agentflow saves all its state there, so a run can stop and later resume where it left off.

pytest

The standard Python test runner. A command like python3 -m pytest exits with code 0 when every test passes, and non-zero otherwise. agentflow uses that exit code as an automatic pass/fail check.

4. Part B: agentflow, the problem it solves

Suppose you ask Claude to write a function. It returns code that looks right. Is it right? You don't know until you test it. If it's wrong, you paste the error back and ask again. If the job has five steps, you do this five times, watching every step. That's "babysitting an agent".

agentflow automates the babysitting with two ideas:

IdeaWhat it doesWhere it lives
The loopProduce → check → if it failed, send the error back and try again (up to 4 attempts in total).Inside one task
The graphDecide which tasks exist, which can run at the same time, and which must wait for another's output.Between tasks

Plus three supporting ideas:

  • Persistence: every change is saved to SQLite, so a crashed or interrupted run can be resumed.
  • A human gate: tasks marked as risky ask a human before running. By default the answer is "no".
  • Learning: when a task fails a check and then passes, the failure is saved. A human can turn recurring failures into permanent rules for future runs.
Two kinds of worker. The text roles (researcher, implementer, reviewer, planner) run with all tools turned off: text in, text out, stored in the database. The coder role, used by the fix command (Chapter 8.7), is the one exception. It can read and edit files, but only inside a throwaway copy of your repo, and its output is a diff that you review and apply yourself. No worker can browse the web, and none changes your actual checkout.

5. agentflow vocabulary

TermMeaning
TaskOne unit of work. Has an id, a worker name, a spec (instructions), deps (task ids whose output it needs), checks (names of check functions), requires_approval, and an optional timeout in seconds.
PlanA list of Tasks. It's just data. It can be written by hand as JSON or produced by the planner.
WorkerA function that does a task: takes a Context, returns output. In the CLI every worker is a Claude call under some role.
CheckA function (task, output) → None or str. None means pass. A string is the error, which is sent back to the worker.
ContextWhat a worker receives: the task, inputs (dependency outputs), feedback (errors from earlier attempts), lessons, attempt number, and meta (a dict for reporting cost).
RunOne execution of a plan, named by a run id like report. Its state lives in SQLite under that id.
ApproverA function (task) → bool asked before a gated task runs. The default always returns False.
LessonThe first line of a check error that a task later fixed. Stored per worker type.
RoleIn the CLI, the worker names: researcher, implementer, reviewer, plus planner for planning. Each has a prompt in .claude/agents/.

Task statuses

stateDiagram-v2 [*] --> pending pending --> running: all deps done pending --> skipped: a dep failed, skipped or rejected running --> done: checks pass running --> failed: 4 attempts used up running --> rejected: approver said no

If the process dies while a task is running, resuming sends a normal task back to pending and marks a gated task failed (Chapter 7.3).

failed, skipped and rejected are the blocking statuses: any task depending on one becomes skipped.

7. The engine, line by line (core.py)

7.1 Data types

@dataclass
class Task:
    id: str
    worker: str                       # name in the worker registry
    spec: dict = {}                   # instructions / params
    deps: list[str] = []
    checks: list[str] = []            # names in the check registry
    requires_approval: bool = False
    timeout: float | None = None      # seconds per attempt

Worker = Callable[[Context], Any]            # sync or async
Check  = Callable[[Task, Any], str | None]   # None = pass
Approver = Callable[[Task], bool]

Workers and checks are referred to by name. That's why a plan can be plain JSON and a run can be resumed from the database alone: the database stores names, and the program supplies the functions.

7.2 validate(tasks, workers, checks)

Runs before anything else and raises PlanError for duplicate ids, unknown worker, unknown check, unknown dependency, or a dependency cycle (found by TopologicalSorter.prepare()). A bad plan never starts.

7.3 Store: the SQLite layer

Two tables. The database is opened in autocommit mode, so every write is saved immediately.

tasks (run, id, def, status, attempts, output, feedback)   -- one row per task per run: CURRENT state
events(run, ts, task, kind, data)                          -- append-only history
Event kindLogged when
run_start / run_endA run begins or finishes (run_end includes every task's status)
attemptAfter each attempt: number, errors, and meta such as cost
skippedA task is skipped because a dependency blocked
approvalThe approver was asked, with its answer
lessonA task passed after failing; holds the worker name and the errors it fixed
plan(CLI) the planner call's cost
reviewed(CLI) a human approved or rejected lessons, logged under the pseudo run _lessons

Important methods:

  • init(run, tasks): inserts any new tasks as pending (existing rows are left alone, using INSERT OR IGNORE). It also handles crash recovery: any task still marked running must have been interrupted. A normal task goes back to pending with the note "Interrupted attempt." A gated task becomes failed, because it may have done something irreversible that a human must reconcile first.
  • load / save / log / events: read and write rows.
  • lock_run(run): makes sure only one process works on a run at a time. It uses an in-memory set plus an OS file lock (fcntl.flock) on <db>.<sha256 of run id>.lock.
  • lesson_counts(): for each worker, each lesson's first line (max 300 characters) and how many tasks hit it, newest first. lessons(worker) returns the top 20.

7.4 Orchestrator.run: the scheduler

Orchestrator(workers, checks, store, approver, max_corrections=3, concurrency=4)
await orch.run(run_id, tasks)   # start a run
await orch.run(run_id)          # resume it from the database

The steps:

  1. Take the run lock. If tasks were given, validate them and init them. Then load the state from the database and validate it again (the database is the source of truth).
  2. Compute a topological order once.
  3. Loop: walk the tasks in that order. For each pending task that isn't already running:
    • if any dependency is blocking (failed, skipped, rejected), mark it skipped. Because the walk follows topological order, skips spread down the graph in a single pass;
    • else if every dependency is done, start it as an asyncio task (_execute);
    • otherwise leave it waiting.
    If nothing is running, stop. Otherwise wait until any one running task finishes (FIRST_COMPLETED), then walk again.
  4. In a finally block, cancel anything still running. Log run_end and return the state.

7.5 _execute: the loop inside one task

flowchart TD START(["task is pending"]) --> DEPS{"did all its deps finish?"} DEPS -->|"a dep failed or was skipped"| SKIP(["skipped"]) DEPS -->|yes| GATE{"requires_approval?"} GATE -->|"yes: ask approver"| REJ(["rejected"]) GATE -->|"no, or approved"| CALL CALL["call the worker with Context:
spec + dep outputs + past errors + lessons"] --> CHECK CHECK{"run every check"} --> PASS{"all pass?"} PASS -->|yes| DONE(["done: output saved"]) PASS -->|"no: errors become feedback"| TRIES{"fewer than 4 attempts?"} TRIES -->|yes| GATE TRIES -->|no| FAIL(["failed: dependents get skipped"])

Details worth knowing:

  • It waits on the semaphore first, so at most concurrency tasks run at once.
  • It loops while attempts <= max_corrections: 1 attempt plus 3 corrections, so 4 attempts at most. The attempt count is saved, so resume continues within the remaining budget.
  • Approval is asked on every attempt, before the worker runs. A "no" makes the task rejected.
  • A worker exception or timeout doesn't crash the run. It becomes the error "worker error: TypeName: message" and counts as a failed attempt.
  • On success, the earlier feedback (minus worker error: and Interrupted attempt lines, which are infrastructure problems, not lessons) is logged as a lesson.
  • Only this task is retried. Finished tasks keep their output, and independent branches keep going.

7.6 Calling workers: _call and _call_sync

Async workers are awaited directly with asyncio.wait_for(..., timeout). Sync workers, such as the CLI's subprocess call to Claude, run in a thread via asyncio.to_thread so they don't block other tasks.

Python can't kill a thread. If a sync worker times out, the engine still waits for the thread to actually finish before retrying. That's what the asyncio.shield + gather code is for. Otherwise a slow old attempt could overlap with the retry. So blocking workers should set their own deadlines, as the CLI does with subprocess.run(timeout=...).

7.7 _verify: running checks

First, the output must be JSON-serializable, because it has to be stored in SQLite. Then every check named in the task runs. A check that raises becomes an error string, not a crash. Each error is prefixed with the check's name, e.g. has_keys: missing keys ['cost']. The returned list is empty when everything passed.

8. The Claude CLI (__main__.py)

8.1 Commands

Run from inside agentflow/. Global flags come before the command.

python3 -m agentflow [--db .workflow/runs.db] [--jobs 4] [--skills .claude/skills]
                     [--effort medium] [--max-output-tokens 8000]  COMMAND

  run NAME --objective "text" [--constraints-from FILE]   Claude plans, then runs
  run NAME --plan FILE                                    run a hand-written plan
  fix NAME --issue "text" --check "cmd" [--repo DIR]      fix a bug in a git repo; result is a patch
          [--readonly PATHSPEC ...]
  resume NAME                                             continue an interrupted run
  status NAME                                             print state, run nothing
  lessons [--propose [--min-count 2] | --approve ROLE | --reject ROLE]

Output: the final state of each task as JSON on stdout, and on stderr a line like agentflow: 4 Claude calls, $0.1200 reported cost. run and resume exit with code 1 if any task didn't finish done.

8.2 --objective vs --plan

--objective--plan
Who writes the task listClaude (the planner role)A JSON file
Extra Claude callYesNo
Same tasks every runNoYes
Checks availablecontains onlycontains and command (run real tests)
Good forOpen-ended writing ("draft a design")Work with a known shape and a test ("write slugify; pytest must pass")

Planner-generated tasks never get the command check. That's deliberate: a model should never choose what code gets executed on your machine.

8.3 claude(role, payload, ...): one Claude call

claude -p --tools "" --setting-sources project --output-format json \
       --no-session-persistence --effort medium
# stdin  = body of .claude/agents/<role>.md + "\n\n" + JSON payload
# env    = CLAUDE_CODE_MAX_OUTPUT_TOKENS=8000
# timeout = task.timeout or 180 seconds
  • --tools "" turns off every tool, so the call is text in, text out.
  • Effort and the output cap stop runaway answers. The README records one call at the default effort producing 76,897 tokens and costing $1.56 for a 1.4 KB answer.
  • It counts calls in meta before calling, records cost even when the call fails, and counts timeouts separately (a killed call reports no cost, so the total is then a lower bound).
  • It raises an error if the envelope can't be parsed, the exit code is non-zero, is_error is set, or result isn't a string. The engine turns that into a failed attempt.

8.4 work(opts, ctx): the worker for every role

All three roles share one worker function. It sends this payload:

{"task": spec, "dependencies": {dep_id: output}, "failure": [errors so far],
 "constraints": "<approved skill text for this role>", "attempt": n}

The task's spec.effort, if set, overrides --effort.

8.5 The two checks

CheckSpec fieldsPasses when
containscontains: [str, ...]Every string appears in the output
commandoutput_file, command: [argv], optional fixtures, command_timeout (default 120)The command exits 0

How command works: it makes a fresh temporary folder, copies fixtures/ into it (for example a pytest file), writes the output to output_file (removing one surrounding Markdown code fence first), replaces {python} in the command with the current interpreter, and runs it. It refuses an output_file that would land outside the temp folder. On failure, the first line of the error is pytest's FAILED/ERROR lines (or the last output line), followed by the last 3000 characters of the log. That first line becomes the lesson.

The command runs model-written code without a sandbox. Only use plans you wrote yourself, or run inside a container.

prepare() checks command specs up front and turns fixtures into an absolute path relative to the plan file, so resume works from any folder.

8.6 plan(objective, constraints): the planner

Calls the planner role, which must return a raw JSON array. Each row becomes a Task:

{"id": "draft-design", "role": "implementer", "brief": "...",
 "depends_on": ["research"], "contains": ["## Risks"], "risk": "contained|wide|irreversible"}
  →  Task(id, worker=role, spec={brief, contains}, deps=depends_on,
          checks=["contains"], requires_approval = (risk == "irreversible"))

The planner's constraints are the strings from --constraints-from plus every approved *-constraints skill, so learned rules shape how the work is split.

Approval in the CLI: the CLI uses the engine's default approver, which always says no. Any irreversible task is therefore rejected and its dependents are skipped. A human-in-the-loop approval flow exists only in the Python API (cli_approver).

8.7 Fixing an issue: fix and the coder worker

This is the one command that changes code in a real repository. You describe the bug and give a command that fails now and should pass once it's fixed:

python3 -m agentflow fix bug-123 --repo ~/work/app \
  --issue "average() adds 1 to the result" \
  --check "python -m pytest -q tests/test_stats.py" --readonly tests/
# → .workflow/bug-123-fix.patch   then: git -C ~/work/app apply <patch>
flowchart TD I["fix NAME --repo --issue --check --readonly"] --> PIN["pin the repo's current commit"] PIN --> PRE{"run the check
on that commit"} PRE -->|passes| REF(["refused: the check
can't detect the issue"]) PRE -->|"fails (expected)"| W["fresh git worktree:
Claude reads and edits files,
may run only the check"] W --> D["output = the staged diff"] D --> C["diff_command, in another fresh worktree:
apply the diff, refuse read-only edits,
run the check"] C --> OK{"passed?"} OK -->|yes| P(["patch file:
you review, then git apply"]) OK -->|"no: output fed back"| T{"fewer than 4 attempts?"} T -->|yes| W T -->|no| F(["failed"])
  • Gate first. pin_repo records the repo's current commit (spec.base), then runs the check on it once, before any Claude call. If the check already passes, it can't detect the bug, so the run is refused. If it fails, the first line is printed (stop there if it's a setup problem such as a missing module) and the full output becomes spec.failing_check, Claude's starting evidence.
  • Worktrees. git worktree add makes an extra checkout of a commit in another folder, sharing the same .git. The worktree() helper makes one in a temp folder and always removes it afterwards. Every attempt and every check gets its own, so a failed attempt leaves nothing behind and retries start clean.
  • The coder call (code()) runs claude -p inside the worktree with --tools Read,Edit,Write,Glob,Grep,Bash --restricted --permission-mode dontAsk and allows Bash only for the exact check command. --restricted ignores the target repo's Claude settings and hooks and keeps file tools inside the worktree. dontAsk refuses anything not allowed, since nobody is there to answer. The default time limit is 900 seconds.
  • The output is a diff: git add -A (excluding clutter like __pycache__/ and node_modules/), then git diff --cached --binary. It's plain text, so storage, resume and lessons work unchanged.
  • The diff_command check fails an empty diff, applies the diff to another fresh worktree, fails if it touches a --readonly path (so Claude can't "fix" a bug by editing the tests), then runs the check. A failure is fed back as usual.
  • Result: for every finished coder task, the CLI writes <run>-<task>.patch next to the database and prints the git apply command. Your checkout is never touched, and uncommitted changes in it aren't included.
  • Limits: the planner can't assign coder tasks (only humans pick what edits code). In a hand-written plan, every coder task starts from the same base commit, so a dependency's diff arrives as text, not applied. The check runs model-written code without a sandbox.

Recorded run (November 2026): a one-line bug in a toy repo was fixed in 1 call, 10 seconds, $0.04.

9. Roles, skills and the learning loop

9.1 Roles (.claude/agents/*.md)

RoleJob (summary of its prompt)
plannerTurn an objective into a JSON array of tasks with real data dependencies only, literal contains markers, and a risk level. Don't do the tasks.
researcherSynthesise the evidence supplied, cite it, name unknowns.
implementerProduce exactly the requested artifact. On a correction, fix the reported failure and keep valid content.
reviewerEvaluate or integrate other tasks' outputs, citing concrete evidence.
coderMake the smallest change that fixes the issue in a disposable checkout. Don't touch tests or read-only paths. Run only the check. Finish with a short summary.

The CLI sends only the body after the frontmatter. Fields like tools: Read, Glob, Grep matter only when the same files are used as subagents in an interactive Claude Code session.

9.2 Skills (.claude/skills/)

plan-project, execute-task and verify-work are short instruction files for interactive Claude Code sessions in this folder. The CLI doesn't use them. Approved lessons are also installed here, as <role>-constraints/SKILL.md.

9.3 The learning loop

flowchart LR A["task fails a check,
then passes on a retry"] --> L["first line of the error
saved as a lesson for that role"] L --> P["lessons --propose
(lessons seen in 2+ tasks)"] P --> H["a human rewrites it
as a general rule"] H -->|"--approve"| S[".claude/skills/role-constraints/SKILL.md"] H -->|"--reject"| X["thrown away"] S --> PL["planner (on --objective runs)"] S --> W["workers of that role"]
  1. lessons lists unreviewed lessons per role with counts.
  2. lessons --propose writes a draft to .workflow/proposals/<role>-constraints/SKILL.md (plus lessons.json) for lessons seen in at least --min-count tasks. If a skill already exists, the draft starts from it.
  3. A human edits the draft, rewriting raw errors like command: exited 1: FAILED test_max_50_chars… into general rules like "URL slugs are at most 50 characters."
  4. --approve ROLE copies it into .claude/skills/. --reject ROLE discards it. Either way the lessons are marked reviewed and won't be proposed again.
Why a human in the middle? Raw check output is specific to one task and would mislead unrelated tasks. So raw lessons are never sent to Claude. Only reviewed rules are, with HTML comments and frontmatter stripped.

10. The irreversible-command guard

This is separate from the engine. It protects you when you use Claude Code interactively in agentflow/.

  • .claude/settings.json registers guard.py as a PreToolUse hook on the Bash tool.
  • guard.py reads the proposed command and checks it against the regexes in irreversible.json. The first match wins.
  • A match prints a decision: deny (blocked) or ask (Claude Code asks you). No match prints nothing, so the command runs normally.
  • If the rules file is broken, the guard answers ask for every command. It never silently lets everything through.
DecisionMatches
denyrecursive rm of /, ~ or $HOME
askrecursive rm; git push; git reset --hard, clean -f, restore; branch/tag deletion, history rewrites; package publishing; terraform/kubectl/helm changes; deploy scripts; DROP/TRUNCATE TABLE
It matches raw text, so it's a guard against honest mistakes, not a security boundary. Clever quoting can get past it, and it also fires on harmless text like echo "git push". In headless claude -p, nobody can answer "ask", so it acts as a denial.

13. Self-check quiz, glossary and FAQ

Quiz

Answer each one before reading the answer.

  1. What's the maximum number of times one task's worker can run in a run?
    Four: 1 attempt plus max_corrections (3).
  2. Task B depends on A. A fails. C depends on nothing. What happens to B and C?
    B is skipped. C still runs and can finish.
  3. Why does the engine refer to workers by name instead of storing the functions?
    So plans are plain data (JSON) and a run can be resumed from the database, with the program supplying the functions.
  4. The process crashes while a normal task and a gated task are running. What happens on resume?
    The normal task goes back to pending (with "Interrupted attempt.") and retries within its remaining budget. The gated task becomes failed so a human can reconcile any side effects.
  5. Why can't the planner produce a command check?
    So a model never chooses what gets executed. command runs unsandboxed, so only hand-written plans may use it.
  6. Can an agentflow worker edit files in your repository?
    The text roles can't: their tools are off. The coder (fix) edits only a throwaway worktree and returns a diff. Your checkout changes only when you git apply the patch.
  7. Why does fix run your check before calling Claude?
    A check that already passes can't tell whether the bug is fixed, so the run is refused. A failing check's output is shown to you (to catch setup problems) and given to Claude as evidence.
  8. When is a lesson recorded, and when does it reach Claude?
    Recorded when a task passes after failing a check (crashes and timeouts don't count). It reaches Claude only after a human proposes, rewrites and approves it as a skill.
  9. An --objective run's planner marks a task irreversible. What happens?
    It becomes a gated task. The CLI's approver always says no, so it's rejected and its dependents are skipped.
  10. What does the guard hook do in an agentflow run?
    Nothing. Text workers have no tools, and the coder runs with --restricted, which ignores project settings and hooks. Its Bash is limited to the check command instead. The hook only protects interactive Claude Code sessions in this folder.
  11. In tmux, what's the prefix key, and what do Ctrl+h/j/k/l do?
    C-s. They move between tmux panes and Neovim splits (vim-tmux-navigator).

FAQ

Do I need tests before using --plan with command? Yes. The test file must already be in fixtures/. An earlier task's output can't become a fixture, and tests written by the same model would only check its own assumptions.

When should I use fix? When a bug can be shown by a command that fails now and should pass once it's fixed: a failing test, or a small script that reproduces it. Write that first. Without one, use Claude Code directly.

When should I not use agentflow? Mechanical edits (renames: use your editor), anything that needs the internet, and one-off questions.

Why not a framework like LangGraph? The engine is a few hundred lines of standard-library asyncio. A framework would duplicate the scheduling and checkpointing and add a heavy dependency (see the README's "Design review").

Where do I go next? agentflow/README.md (reference), agentflow/DIAGRAMS.md (diagrams on GitHub), then read core.py top to bottom. With this guide it should read easily.
